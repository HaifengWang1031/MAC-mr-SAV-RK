# Linear MAC Stokes acceleration research

Date: 2026-09-27

Status: accepted optimizations integrated into `main`

## Executive conclusion

For the current uniform rectangular, constant-coefficient MAC problem, keep
`TensorStokes` as the primary linear solver. A synchronized pair of independent
preconditioned-CG recurrences was implemented and tested, but it is slower than
the original sequential-column SciPy CG on this NumPy/SciPy stack, so that
experimental implementation is not retained. Serial Numba MAC `D/D.T` stencils
and safe reuse of disposable FFT buffers do provide a reproducible speedup and
are now the default TensorStokes operator path.

Ranked recommendations:

1. Keep the accepted serial matrix-free `D/D.T` and FFT-buffer reuse path.
2. Reduce or avoid transforms only through a demonstrably safe preconditioner
   or Schur formulation; the current Krylov tolerance cannot be relaxed.
3. Revisit batched CG only with a column-contiguous transform/stencil path that
   removes the measured array-reduction and sparse-`matmat` penalties.
4. Defer true block CG: two RHS and 4--8 scalar iterations leave little room to
   repay its rank handling and dense block algebra.
5. Use PETSc/MPI only for larger/distributed problems or when nonuniform grids,
   variable coefficients, or geometry invalidate tensor diagonalization.

Do **not** prioritize wrapping the whole solver in Numba or increasing SciPy FFT
workers. The first cannot compile through the important SciPy calls in nopython
mode, and the second has already shown no useful scaling on this workload.

## Current implementation and evidence

[`TensorStokes`](../solver/mac/tensor_stokes.py) already batches the initial and
final velocity Helmholtz transforms over all RHS columns. Inside the pressure
solve, however, `scipy.sparse.linalg.cg` is called once per column. Each scalar
CG Schur action performs `D.T`, a velocity inverse using DST/DCT, and `D`.
SciPy's CG interface accepts one RHS of shape `(N,)` or `(N, 1)`, not an
`(N, nrhs)` block, so this loop is expected from the public API
([SciPy CG documentation](https://docs.scipy.org/doc/scipy/reference/generated/scipy.sparse.linalg.cg.html)).

The reproducible worker benchmark is
[`reports/timings/20260927T114004-9da6eaf4-stokes-workers/timings.json`](../reports/timings/20260927T114004-9da6eaf4-stokes-workers/timings.json),
generated by
[`benchmark_stokes_workers.py`](../experiments/kolmogorov_adaptive/benchmark_stokes_workers.py).
It uses SciPy 1.18.1, NumPy 2.5.3 and Numba 0.67.0 with external thread counts
fixed to one.

| Grid and work | workers=1 | workers=2 | workers=4 | workers=8 |
|---|---:|---:|---:|---:|
| 128², 20 two-RHS solves | 0.2413 s | 0.2488 s | 0.2417 s | 0.2404 s |
| 512², 5 two-RHS solves | 1.3104 s | 1.4564 s | 1.3115 s | 1.3090 s |

The Schur iteration averages remain exactly 4.95 and 7.6 per RHS. Process CPU
time is approximately equal to wall time at every worker count, so there is no
evidence of useful concurrent transform work. SciPy documents `workers` only as
the maximum number available for parallel computation; it does not promise
speedup for every transform size or batch
([`dct`](https://docs.scipy.org/doc/scipy/reference/generated/scipy.fft.dct.html),
[`set_workers`](https://docs.scipy.org/doc/scipy/reference/generated/scipy.fft.set_workers.html)).
For this repository, `workers=1` is therefore the evidence-based default.

A separate 512² cProfile probe of three two-RHS solves measured 0.804 s total:
0.508 s in transforms (about 63%), 0.148 s in sparse matrix multiplication
(about 18%), and 0.148 s in CG/vector work (about 19%). This profile should be
made a persistent benchmark before optimization, but it already bounds the
opportunity: even eliminating **all** sparse multiplication would improve total
time by at most `1/(1-0.18) = 1.22x`. Replacing only `D/G` has a lower ceiling.

### Synchronized independent CG result

Gate A was tested with
[`benchmark_batched_cg.py`](../experiments/kolmogorov_adaptive/benchmark_batched_cg.py).
The formal artifact is
[`reports/timings/20260927T120048-33ca6d77-batched-schur-cg/timings.json`](../reports/timings/20260927T120048-33ca6d77-batched-schur-cg/timings.json).
It fixes SciPy FFT workers to one, alternates execution order, varies viscosity
over `[8e-6, 2e-5]`, and reports three-repeat medians excluding backend setup.

| Grid and work | Sequential CPU | Synchronized CPU | Synchronized change |
|---|---:|---:|---:|
| 128², 20 two-RHS solves | 0.2577 s | 0.3142 s | 21.9% slower |
| 512², 5 two-RHS solves | 1.4008 s | 1.8013 s | 28.6% slower |

Wall-time changes are essentially identical. One-RHS controls differ by at most
about 1.5%, while all two-RHS iteration traces match exactly. Maximum relative
differences are `6.5e-16` for velocity and `1.4e-14` for pressure, so this is a
performance rejection rather than a numerical failure.

An initial implementation using reductions over two-column arrays was even
slower. Column-contiguous CG state and per-column BLAS reductions reduced the
penalty, but did not remove it. Profiling attributes the remaining loss to
strided batched transforms, sparse matrix-matrix kernels, mean reductions, and
extra two-column memory traffic. The reduced number of Python/operator calls is
too small a benefit at only 4--8 Schur iterations. Gate A therefore fails its
required 15% speedup and the original sequential path remains the default.

### Matrix-free MAC operators and FFT buffer reuse

Gate B was implemented with serial cached Numba kernels for packed one- and
multi-column `D` and `D.T`. The one-column specialization is important because
the accepted scalar CG path applies most Schur actions one column at a time.
SciPy transforms receive `overwrite_x=True` only for disposable temporaries;
the original RHS remains unchanged, and tests verify identical output.

The five-repeat linear artifact is
[`reports/timings/20260927T122214-d18c9b76-matrix-free-stokes/timings.json`](../reports/timings/20260927T122214-d18c9b76-matrix-free-stokes/timings.json).

|---|---:|---:|---:|
| 128², one RHS, 20 solves | 0.0999 s | 0.0922 s | 1.092× |
| 128², two RHS, 20 solves | 0.2163 s | 0.1959 s | 1.106× |
| 512², one RHS, 5 solves | 0.5563 s | 0.5154 s | 1.078× |
| 512², two RHS, 5 solves | 1.1630 s | 1.0717 s | 1.087× |

The 512² two-RHS reduction is about 8.0%, meeting Gate B. Iteration traces are
identical; maximum relative differences are `8.1e-16` for velocity and
`2.7e-14` for pressure. CPU and wall speedups agree. Numba warmup is about
0.10 s on this host and is excluded from repeated-solve timings.

The 128² ten-step artifact is
[`reports/timings/20260927T125431-bd5c5897-matrix-free-10-step/timings.json`](../reports/timings/20260927T125431-bd5c5897-matrix-free-10-step/timings.json).
Across fixed and random schedules, ordinary SDIRK2/3 speedups are

optimized-path divergence is `7.7e-13`.

A tolerance scan found that relaxing Schur CG from `1e-12` causes the existing
full-divergence gate to fail on representative 512² random right-hand sides as
soon as an iteration is saved. The tolerance therefore remains unchanged.

### Exact linear and nonlinear reuse audit

The stage formulas were audited without changing their numerical method or
floating-point reduction order. The accepted exact reuse is:

- construct the two velocity spectral shifts once per Stokes solve rather than
  once per Schur application;
- reuse the final `D.T @ pressure` in both the velocity RHS and explicit momentum
  defect;
- cache each stage `K @ velocity` for every later SDIRK3 occurrence and for the
  mrSAV defect;
- evaluate the MAC stage divergence once and use the same value for physical
  divergence and continuity, while the spectral model retains its two distinct
  definitions;
- reuse one diagnostic `K @ velocity` for both the H1 seminorm and dissipation;
- evaluate the mrSAV negative-response guard norms only when the response is
  actually negative.

Per step, `K @ velocity` calls are now 1/2/3/4 for SDIRK2, SDIRK2-mrSAV,
SDIRK3 and SDIRK3-mrSAV; before reuse they were 1/3/6/10. MAC stage-divergence
applications are halved from 4/4/8/8 to 2/2/4/4. A focused regression fixes
these counts.

The nonlinear term is already evaluated exactly once at each distinct RK node:
two times per SDIRK2 step and four times per SDIRK3 step. There is no duplicate
`N(u)` within a step to cache. In particular, the identity
`<B,V-cW> = <B,V> - c<B,W>` is not substituted into the mrSAV scalar residual,
because that would change floating-point reduction order and could move a value
across the existing residual gate.

The final five-repeat ten-step record above includes these exact-reuse changes.
Profiling shows that the removed linear/diagnostic work is only a few percent of
total time because Stokes transforms still dominate; the reuse is worthwhile but
cannot produce a large multiplicative speedup by itself.

The pre-decoupling commit `13d8a26` was compared directly with the current full
optimization path using the same 128² Kolmogorov problem, four schemes, fixed and
seeded-random ten-step schedules, solver tolerances, Python environment, and one

backend setup and integration but excludes imports and Numba warmup.

|---|---|---:|---:|---:|---:|
| SDIRK2 | fixed | 0.5399 s | 0.1463 s | 3.690× | 72.9% |
| SDIRK2 | random | 4.1661 s | 0.1378 s | 30.241× | 96.7% |
| SDIRK2-mrSAV | fixed | 0.6562 s | 0.2395 s | 2.740× | 63.5% |
| SDIRK2-mrSAV | random | 4.3662 s | 0.2433 s | 17.947× | 94.4% |
| SDIRK3 | fixed | 0.6795 s | 0.2417 s | 2.812× | 64.4% |

| SDIRK3-mrSAV | fixed | 0.8965 s | 0.4476 s | 2.003× | 50.1% |
| SDIRK3-mrSAV | random | 4.5997 s | 0.4445 s | 10.349× | 90.3% |

Summing the four case medians, fixed-step CPU time falls from 2.7722 s to

1.0581 s (16.477×, 93.9%). The large random-step gain comes primarily from

The maximum final-velocity relative difference is `6.0e-13`; optimized maximum
divergence is `7.7e-13`, below the configured Stokes gate. The raw record is
[`reports/timings/20260927T130948-4cf985b6-initial-vs-optimized-10-step/timings.json`](../reports/timings/20260927T130948-4cf985b6-initial-vs-optimized-10-step/timings.json).

The broader correctness and timing evidence is recorded in
[`docs/validation.md`](validation.md): at 128², the tensor backend removes the
random-step refactorization penalty, matches the direct backend to roughly
`1e-12` in velocity, and retains full momentum-residual and divergence checks.

## Method assessment

### 1. Why whole-solver Numba wrapping is limited

The hot path calls `scipy.fft.dct/dst/idct/idst`, SciPy CSR multiplication,
`LinearOperator`, and SciPy CG. Numba's useful performance mode is nopython;
object mode retains Python-object dispatch and offers little benefit
([Numba performance guidance](https://numba.readthedocs.io/en/stable/user/performance-tips.html)).
The numba-scipy support table lists sparse support as experimental boxing,
unboxing, `shape`, `ndim`, and `copy`; it does not provide CSR matmul or SciPy
FFT lowering
([numba-scipy reference](https://numba-scipy.readthedocs.io/_/downloads/en/latest/pdf/)).

Consequently, adding `@njit` around `TensorStokes.solve` cannot fuse or
recompile the 63% transform component and cannot compile the existing SciPy CG
driver. The viable JIT target is new array-loop code that stays entirely in
nopython mode: direct `D/D.T` stencils, fused CG vector updates, and reductions.
Keep `fastmath=False`; changes in reduction order can move an adaptive error
estimate across an acceptance boundary.

### 2. Compiled MAC `D/G` stencils

`D` has only two to four known entries per pressure cell, while `G=-D.T` is the
corresponding face difference. CSR is already intended for fast matrix-vector
products ([SciPy CSR documentation](https://docs.scipy.org/doc/scipy/reference/generated/scipy.sparse.csr_matrix.html)),
but it still loads row pointers, column indices, and values for a stencil whose
indices and coefficients are known from `(nx, ny, hx, hy)`. Sparse matvec is
commonly bandwidth limited; the original multicore SpMV study by Williams et
al. analyzes this optimization constraint
([DOI 10.1145/1362622.1362674](https://doi.org/10.1145/1362622.1362674)).

A direct Numba kernel can operate on one or two RHS columns without sparse
metadata and can fuse mean removal or selected vector updates. `prange` is
available for independent rows, but the programmer must prove the absence of
cross-iteration dependencies
([Numba parallel-loop documentation](https://numba.readthedocs.io/en/stable/user/parallel.html)).
Benchmark serial `njit` first: 128² kernels may be too small to repay thread
scheduling, and process-level member parallelism should not be oversubscribed.

### 3. Synchronized independent CG versus block CG

**Synchronized independent CG** stores `X, R, Z, P` as two-column arrays but
retains a separate scalar `alpha`, `beta`, residual norm, and convergence state
for each column. The Schur operator and preconditioner are called once on the
active column block. A converged column is frozen while the other continues.
In exact arithmetic this is the same pair of scalar PCG methods as today; its
purpose is batched transform/stencil execution, not a different Krylov space.

**Block CG** instead uses small dense block coefficients and a shared block
Krylov space. It can reduce iterations and increase arithmetic intensity for
multiple RHS; O'Leary developed block CG specifically for simultaneous systems
([original paper](https://doi.org/10.1016/0024-3795(80)90247-5)). The cost here
is less attractive because there are only two RHS and current convergence takes
about 3.5--7.6 iterations per RHS. Moreover, zero, proportional, or nearly
dependent mrSAV RHS can make residual/search blocks rank deficient. Robust block
methods require rank handling or reformulation; this is the central issue in
Dubrulle's original analysis
([ETNA 12, 216--233](https://etna.ricam.oeaw.ac.at/volumes/2001-2010/vol12/abstract.php?pages=216-233)).

The synchronized method remains a useful correctness reference, but the measured
implementation is not a production candidate. Block CG is even less attractive
until a faster column-contiguous operator path changes this cost balance.

### 4. Process-level parallelism across adaptive members

The eight scheme/controller members in `run_campaign` are independent but are
currently executed sequentially. Running members in spawned processes can
reduce campaign wall time without changing a single Stokes solve. The parent
must remain the sole writer of `batch.json`; each child writes only its own run
directory and returns its manifest to the parent.

Each process should use SciPy FFT workers, BLAS/OpenMP, and Numba threads equal
to one initially. Numba explicitly warns that combining multiple processes
with each process's full thread pool oversubscribes the machine, and documents
thread masking for this use case
([Numba threading-layer documentation](https://numba.readthedocs.io/en/stable/user/threading-layer.html)).
Use a spawn-based process context to avoid inherited thread-runtime state.
This optimization reduces elapsed campaign time, not aggregate CPU work.

### 5. When PETSc/MPI is worthwhile

PETSc is not a faster switch for the present 128²--512² tensor-diagonalizable
problem. It becomes worth engineering when at least one condition holds:

- the problem no longer has uniform rectangular, separable, constant-coefficient
  velocity blocks;
- one process cannot meet memory or wall-time requirements, or multi-node
  execution is required;
- measurements at 1024² or larger show communication and setup amortized over
  the real sequence of shifted solves.

PETSc's `DMSTAG` directly represents logically rectangular staggered grids
([DMSTAG documentation](https://petsc.org/release/manualpages/DMStag/DMSTAG/)),
and `PCFIELDSPLIT` provides Schur-complement block preconditioning
([PCFIELDSPLIT documentation](https://petsc.org/release/manualpages/PC/PCFIELDSPLIT/)).
For a Schur-space CG implementation, the operator and preconditioner must remain
symmetric positive definite; PETSc states this requirement explicitly
([KSPCG documentation](https://petsc.org/release/manualpages/KSP/KSPCG/)).

The historical PETSc results in `docs/validation.md` compare a distributed
iterative backend with the old direct solver, not with `TensorStokes`: at 512²
the recorded four-rank per-solve time was slower than direct, while at 1024² it
was faster. They do not establish a PETSc/Tensor crossover. The current solver
tree also has no PETSc backend, so this is a separate backend project rather
than a local optimization.

MPI CG additionally introduces global reductions. PETSc provides single-reduction
and pipelined CG variants for large process counts, but its own documentation
positions them for cases where reductions dominate
([KSPCG documentation](https://petsc.org/release/manualpages/KSP/KSPCG/)).
Pressure null-space registration, true residual monitoring, and the repository's
full physical divergence check remain mandatory. PETSc's default stopping norm
may be preconditioned, so it must not replace the existing acceptance checks
([KSP convergence tests](https://petsc.org/release/manual/ksp/)).

## Correctness risks

- **Adjointness:** compiled kernels must preserve `G=-D.T` for the eliminated
  normal-boundary layout, including rectangular grids and both RHS counts.
- **Pressure null space:** every Schur residual, iterate, and preconditioned
  vector must remain mean zero; PETSc must be told about the constant null mode.
- **Stopping semantics:** synchronized CG must apply the current SciPy criterion
  independently to each RHS and freeze converged columns without zero divisions.
- **Block rank loss:** true block CG must handle zero, collinear, and nearly
  collinear RHS; silent regularization is not acceptable.
- **Roundoff and adaptivity:** fused reductions, parallel reductions, and block
  recurrences may alter last bits. Compare accepted/rejected trials and error
  estimates, not only the final state.
- **Oversubscription:** process workers, FFT workers, Numba threads, BLAS threads,
  and MPI ranks must be budgeted together and recorded.
- **Residual definitions:** always retain the explicit momentum defect and full
  MAC divergence checks; an internal Krylov residual alone is insufficient.

## Concrete benchmark and acceptance plan

### Common matrix

Use square grids 128² and 512², plus 1024² where memory permits; include one
12×10 rectangular correctness case. Test one and two RHS, fixed and randomized
positive viscosity sequences over the existing `[8e-6, 2e-5]` interval, and
both zero/proportional and independent two-RHS stress cases. Warm each compiled
path before timing, but record cold-start/JIT time separately. Use at least five
timed repeats, report medians, and record wall time, process CPU time, setup,
iterations per RHS, maximum momentum residual, maximum divergence, and peak RSS.

### Gate A: synchronized independent CG

**Status: failed on 2026-09-27.** Correctness and iteration-count requirements
pass, but 128² and 512² two-RHS CPU/wall time regress by 21.9% and 28.6%.

- Match the current sequential solver within relative `1e-11` for velocity and
  `1e-10` for mean-zero pressure; pass the existing residual/divergence gates.
- Match each scalar RHS iteration count, or differ by at most one only when the
  recomputed true residual explains the stopping difference.
- Reduce 512² two-RHS median solve wall time by at least 15%; regress 128² and
  one-RHS time by no more than 5%.
- Re-run the adaptive direct-versus-tensor smoke test and require identical
  accept/reject decisions.

### Gate B: compiled `D/G`

**Status: passed on 2026-09-27.** The combined serial matrix-free and disposable
FFT-buffer reuse path reduces 512² two-RHS CPU/wall time by about 8.0%, preserves
every scalar-CG iteration trace, and passes the full residual/divergence checks.

- Compare stencil and CSR actions on random and manufactured fields for square
  and rectangular grids; verify the discrete adjoint identity to roundoff.
- Keep `fastmath=False` and test both one- and two-column layouts.
- Require at least 8% additional reduction in 512² two-RHS solve time and no
  more than 5% regression at 128². Reject the optimization if this gate fails;
  the profile gives it a small Amdahl ceiling.

### Gate C: block CG

- Benchmark only against the accepted synchronized-independent implementation.
- Include zero, identical, nearly collinear, and independent RHS and report rank
  decisions, dense 2×2 conditioning, iterations, and true residuals.
- Accept only if it is at least 10% faster at 512² across the representative
  mrSAV cases with no robustness fallback in ordinary runs. Otherwise keep the
  simpler synchronized method.

### Gate D: member processes

- Run the same eight adaptive members with 1, 2, 4, and 8 processes while all
  inner thread counts are one.
- Require at least 2.5× median wall speedup at four processes on the documented
  10-core host, less than 20% aggregate CPU inflation, and no corrupted or
  duplicate batch entries.
- Require identical member status and accept/reject counts; compare states with
  the existing numerical tolerances if result files are not bitwise identical.

### Gate E: PETSc/MPI decision

- Compare Tensor workers=1 against PETSc at 1/2/4/8 ranks on 512², 1024², and
  2048² where feasible, using the same one/two-RHS and shifted-coefficient set.
- Separate setup from repeated solve time and collect PETSc `-log_view`, true
  residual histories, iterations, communication time, and per-rank peak memory
  ([PETSc profiling documentation](https://petsc.org/release/manualpages/Log/)).
- Proceed beyond a prototype only if PETSc is at least 20% faster at a required
  production size, enables a size Tensor cannot run, or supports a required
  nonseparable operator. A direct-versus-PETSc crossover is not sufficient.

## Recommended implementation order

1. Keep sequential-column SciPy CG as the production baseline.
2. Keep serial matrix-free `D/D.T` and FFT-buffer reuse enabled.
3. Re-profile transform count before attempting a new preconditioner.
4. Revisit synchronized or block CG only after operator-layout costs fall.
5. Benchmark PETSc against Tensor at 1024²+ before committing to MPI work.
